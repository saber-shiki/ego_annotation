# Current epistemic model

The stakeholder is not asking for more HOI demo polish. The delivery problem is a productization problem: separated head/camera and hand accuracy driven toward a uniform 5mm ideal, including head/camera, hand wrist/root, all joints, hand surface, visible projection, occlusion stability, semantic clip segmentation/captioning, and a directly callable high-throughput API. The research problem remains HOI physical extraction and should not slow this delivery pipeline.

## First commitments from completed subagents

Serving/API mechanism: the inner serving problem is video-temporal colocation, not merely HTTP. The chosen initial production path is a video-aware async API + custom scheduler + Ray Serve/Ray GPU actors on a private GPU fleet because it is the simplest route for arbitrary PyTorch functions, persistent model residency, batching, and video-affinity scheduling. Triton/PyTriton comes after tensor contracts stabilize; Kubernetes/KServe is deferred outer orchestration; TorchServe should be avoided.

Throughput mechanism: 10k video-hours/week requires about 59.5 realtime streams continuously per module. Every module needs measured `module_speed_x`, GPU utilization, queue wait, batch fill, and load-amortization metrics. Full-rate SAM2 is already the likely budget breaker; hands are not the dominant throughput problem.

Metric mechanism: a useful GT-free metric is disagreement between independent measurement paths. Delivery metrics must route error reduction across the whole target vector: head/camera ATE/RPE/rotation/scale, hand wrist/root, all-joint MPJPE, surface/MPVPE, reprojection, visibility, jitter, caption grounding, and throughput. The selected head/camera promotion benchmark is an in-house fixed-gauge fiducial/mocap lockbox with hidden GT, calibrated sync, and known camera/head extrinsics; public sidecar datasets remain development/regression checks. Current HOT3D sub-10 wrist/root result proves smooth correctability under disclosed GT calibration; deployable hand progress now prioritizes all-joint MPJPE after wrist/root while preserving surface/visibility/stability metrics.

## Live uncertainties
- Which exact minimal module set is necessary and sufficient for sub-centimeter head/camera + hand accuracy without HOI.
- Whether visible drift is dominated by intrinsics, crop/pinhole adapter, coordinate conventions, metric scaling, or stale render layer wiring.
- What API output schema makes provenance, coordinate frames, semantic clips, and QC metrics implementable without HOI baggage.
- Which HOI research bottlenecks are real physical-model limits versus implementation mistakes.

## First-wave synthesis additions

The tomato drift complaint is no longer generic: shipped tomato left/right fused hands have p95 31.6/24.5 px versus WiLoR 2D, with fallback rows around 100 px off and fusion doubling the tail relative to pre-fusion fit. The dominant product fixes are calibrated K, rigid metric space, detector-bounded fusion, final-layer QC, and deterministic renderer.

Delivery can drop HOI/object/factor-graph work without abandoning the 5mm ideal because the metric hand/camera/caption product does not need object-pose/contact optimization in the default path. The current head/camera frontier is weak because no evaluator exists and HaWoR/DROID world evidence is decimeter-class; that evidence selects the first interventions—build the fixed-gauge fiducial/mocap lockbox, reserve optional device calibration/VIO/head-pose fields without requiring them, calibrate synchronization/extrinsics, and repair video-derived trajectory estimates—rather than reducing the target.

Research should not add more HOI factors until it adds measurements: temporal surface correspondence, rigidity statistics, multi-frame fusion, and contact channels surviving occlusion.

Subagent 6 sharpened the delivery auto-research model: delivery has no honest single scalar because self-consistency metrics are gameable. The protected evaluator must be a vector over hand/camera/drift/caption/throughput, with a visual-truth veto and frozen GT/eval bundles. This prevents a loop from lowering H3 reprojection while worsening depth/size H5, or reducing throughput while degrading caption grounding.

Subagent 8 failed operationally (Node heap OOM) but its partial reasoning supports a stable research schema mechanism: HOI output must represent geometry epochs, pose observability, contact posteriors, face provenance, graph liveness, stale joins, and gauge declarations as first-class fields. The research track's schema is not administrative; it is how prior v19 failure modes become impossible to hide.

The canonical HOI extension output is available as `subagents/08_hoi_output_and_metrics.md`, but its public/domain-facing naming must be normalized when incorporated into task packs: use a domain extension such as `org.ego.hoi` / `ego.hoi`, not the internal planning label `research`. It requires full-duration HOI renders and encodes HOI claims as sidecar tables/streams. Its critical mechanism is that HOI claims become falsifiable through row-level provenance: geometry epochs, pose status, contact posterior, occlusion ownership, hand corrections, and graph liveness all have explicit observability/uncertainty fields instead of implicit confidence.

Wave 3 changes the research model in two ways. First, autonomous research is itself blocked until an honest protected evaluator exists: fixed HOT3D slices are too small and overfit-prone, contact GT is proxy-derived, and every GT-free metric can be gamed. The research loop must therefore optimize a vector over HOI state families, require GT/proxy/render co-motion, and reject fixed-slice-only wins. Second, RL cannot repair missing measurements. RL is admissible only as an inference-side approximator after the factor graph is validated: amortized MAP, switch/initializer scheduler, or measurement-coupled feasibility projection. It is invalid as video-to-HOI replacement, proxy reward optimizer, or contact/pose hallucination in unobserved null spaces.

User correction: the primary customer artifact is numeric head/camera, hand, caption, and throughput output; renders are QC/demo views and cannot change the delivered numeric result. Prior language that treated rendering as the result was wrong. A render/projection mismatch diagnoses state/K/crop/renderer wiring, but it is not the mechanism for numeric accuracy. Public API names must use product/domain nouns such as annotation jobs or video analysis jobs; internal planning labels such as delivery/research do not belong in endpoint paths or public-facing schema names. Accuracy targets must be framed as optimization objectives: the task is to push every physical error axis toward the uniform 5mm ideal, report the measured frontier, and name the next error-reduction mechanism per axis.

User correction: if HOI is skipped, SAM2/dense object segmentation is not a delivery prerequisite. Throughput analysis must focus on active delivery lanes: pose source ingestion or camera tracking, hand models/fusion, caption alignment/external-call throughput, API scheduling, and artifact IO. Captioning is not a local GPU lane in the current delivery scope.

Updated 5mm head/camera model: reaching the ideal is an estimator-and-measurement program. The API reserves optional device VIO/SLAM/IMU/head-pose metadata and calibration fields, but inputs are not guaranteed to include them. When metadata is absent, RGB/video-derived tracking remains an estimator to improve and score; when its scale/gauge is weak, the next intervention is to add metric constraints and measure the residual gap. The selected promotion measurement is a protected in-house fixed-gauge fiducial/mocap lockbox. The work is to define the metric pose source contract, calibrate synchronization/extrinsics/distortion/rolling shutter, and evaluate ATE/RPE under fixed metric gauge while reducing error on every release.
